# Permission Mapping: Today's Checks to the Roles & Permissions Matrix

_As of 2026-10-28 · Draft for review · Companion to [Auth, Tenancy and Plan Tiers](2026-10-28-auth-and-tenancy-options.md)_

> Committed as written on 2026-10-28, for review with the code. Where it differs from [Access Matrix and Identity Provider](2026-10-30-access-matrix-and-identity-provider.md), that design note is the current decision.

This is the first step of the matrix work. It covers four things:

- how every endpoint checks access today
- which matrix module and action (view, create, edit, approve, delete) each endpoint maps to
- the starting permissions for the standard roles, so nobody gains or loses access on switch-over
- what the matrix needs beyond module × action

It is cross-checked against the plain-language roles guide, Who Can Do What, which is on the ticket and not kept in the repo. This doc calls it "the roles guide" from here on.

The per-endpoint table is [2026-10-30-access-permission-mapping-endpoints.csv](2026-10-30-access-permission-mapping-endpoints.csv). It has 814 rows, one per endpoint with an inline `@PreAuthorize` check. Another 130 endpoints in WBS, work progress and toolbox talks use guard constants, and are mapped in [their own table](#backend-package-to-matrix-module) below. That's 944 endpoints in all.

| Column | Meaning |
| --- | --- |
| `proposed_module`, `proposed_action` | Where the endpoint lands in the matrix |
| `check_kind` | How it checks access today (see below) |
| `current_roles`, `self_allowed` | The role names it accepts, and whether a user may act on their own record |
| `authority_aliases` | How its old Keycloak permission names map |
| `current_expression` | The check as written today |
| `file` | The controller, relative to `echno-backend/src/main/java/org/tornotron/echno_backend/` |

The CSV was generated by scanning the controllers. Review it module by module during the conversion rather than trusting every row.

## How endpoints check access today

| Kind | Endpoints | What it is | What it becomes |
| --- | --- | --- | --- |
| Role names | 376 | `@orgSecurity.hasAnyOrgRoleForCurrentTenant('system-admin', 'project-manager', …)` and similar | A permission check on the endpoint's module and action |
| Any member | 169 | `@orgSecurity.isMemberOfCurrentTenant()` | `view` (or the endpoint's action) on its module, which the base Member role grants |
| Keycloak permission | 141 | `hasAuthority('vendor:read')`, from Keycloak's permission-token swap | Probably unusable by anyone today (see below). Retired where a newer endpoint covers it, converted otherwise. |
| Domain security bean | 93 | `@inspectionSecurity.…`, `@attendanceSecurity.…`, `@leaveSecurity.…` | The bean's methods are reimplemented on the matrix; the annotations stay as they are |
| Platform admin | 22 | `hasRole('platform-admin')` | A flag in our database; not part of the org matrix |
| Open | 13 | `isAuthenticated()` / `permitAll()`: plan list, org create and summary, registration, current user, payment webhooks | Unchanged |

**Six org role names are used in checks:**

- in the CSV: `system-admin` (376 endpoints), `project-manager` (189), `store-keeper` (100) and `hr-admin` (62)
- in the guard constants below: `site-engineer` (work progress) and `safety-officer` (toolbox talks)

The other three appear in no endpoint check. The roles guide confirms what each one does:

- **`qa-engineer` and `observation-producer`** work through the inspection security bean. The observation producer is a machine login (a camera or sensor) that sends in observations for a person to review.
- **`org-manager`** is a title only. It lets a person be named as someone's manager, but gives no access.

**The Keycloak permissions are probably held by nobody.**

- **What the guide says:** about 125 older actions, mostly in stores, vendors, projects and tasks, can't be used by any role, and the newer versions of those screens work. That matches the 141 `hasAuthority('vendor:read')`-style endpoints here.
- **Why it's plausible:** the resources and policies behind those names are only ever created at runtime through the Keycloak admin endpoints (`KeycloakManagementService`, under `/clients/{clientId}/…`). Nothing seeds them.

If that holds, those endpoints need neither a Keycloak export nor aliases. Each one is either retired, where a newer endpoint covers it, or converted to a matrix check. Before retiring anything, check one token from staging and one from prod for a permission such as `vendor:read`.

**Platform admin was never set up.** Nobody holds the role, so the 22 platform-admin endpoints (plans and pricing) can't be used today. They become usable once platform admin is a flag in our database.

#### Contractor bills: split into four steps

Bills go through separate steps today, and different people are allowed for each. The roles guide's sign-off chain keeps them apart, so that whoever prepares a bill never approves it:

1. Site engineer prepares and measures.
2. Quantity surveyor certifies.
3. Project manager approves.
4. Finance pays.

So bills get their own row, `progress-bills`, with the steps as permissions rather than one `approve`:

| Permission | Guard today | Who has it on day one |
| --- | --- | --- |
| `progress-bills: view` | `READ_GUARD` | Member (today anyone can read bills; see [weak spots](#weak-spots-copied-on-day-one)) |
| `progress-bills: edit` | `BILLING_SETUP_GUARD` (contract billing setup) | System admin, PM |
| `progress-bills: prepare` | `BILL_PREPARE_GUARD` | System admin, PM, site engineer |
| `progress-bills: verify` | `BILL_VERIFY_GUARD` | System admin, PM, site engineer |
| `progress-bills: certify` | `BILL_CERTIFY_GUARD` | System admin, PM |
| `progress-bills: approve` | `BILL_APPROVE_GUARD` | System admin, PM |

The preparer-vs-approver rule ([below](#beyond-module--action)) stops one person certifying and approving the same bill. The guide lists that as a gap today.

The constants make conversion easy: change the constant's value and every endpoint using it follows.

Matrix rows with no backend endpoints of their own (`dashboard`, `reports`, `echno-bot`) only control what the web shows. Reports that read finance or inventory data should check those modules too.

| Endpoint | Action |
| --- | --- |
| `GET` | `view` |
| `POST` | `create` |
| `PUT`, `PATCH` | `edit` |
| `DELETE` | `delete` |
| Path or method mentions approve, reject, verify, review, decide, sign-off, confirm or reverse | `approve` (51 endpoints) |

The 51 approve endpoints are marked in the CSV. Review them by hand. A few may be ordinary edits, and some approvals may use names the pattern misses.

"Self" checks (`isSelfOrHasAnyOrgRole`, `isSelfUser`, `isSelfInCurrentTenant`, about 25 endpoints) stay as they are. A user can always see and act on their own records, such as their own leave and attendance, whatever the matrix says. The matrix adds access to other people's records.

**Two things to settle before seeding:**

1. **Members can read expenses and receipts today.** Six finance endpoints (`/expenses/web`, `/receipts/web` and their paginated and by-id versions) only check membership. Either keep that as a special case (members see their own expenses), or tighten it to `finance: view`. The second option changes current behaviour.
2. **Today's endpoint grants are uneven.** For example, system admin has `vendors` but project manager doesn't, and store keeper can create goods receipts but not indents. The seed copies today's behaviour exactly. Tidying it up is a product decision to make in the Roles & Permissions tab afterwards, not during the migration.

The other `OrgRole` values are also seeded as standard roles:

- **Site engineer:** Member, plus `progress: create, edit`, `progress-bills: prepare, verify` and the inspection permission to report corrective action.
- **Safety officer:** Member, plus `toolbox-talks: create, edit, delete`, and the safety side of `inspections` (raise and sign off safety defects).
- **QA engineer:** Member, plus the quality side of `inspections` (define checklists, raise and sign off quality defects).
- **Observation producer:** the inspection permission to send observations, nothing else. It's a machine login, not a person.
- **Org manager:** Member only. It's a title that lets a person be named as someone's manager.

### Weak spots copied on day one

The seed copies today's access exactly, so the switch-over changes nothing. That means it also copies weak spots the roles guide lists. Fix these first in the Roles & Permissions tab after go-live:

1. **Attachments:** anyone in the company can read, upload, rename and delete attachments on any record (`documents`: Member has full access today). Target: view follows the record's own area; upload, rename and delete need edit there.
2. **Contractor bills:** anyone can read them, including the PDFs and the contract's financial summary (`progress-bills: view` for Member). Target: only the bill chain, project leadership and finance.
3. **Finance:** project managers get the whole area, including the company books and bank accounts. Target: their own projects' cost position only, with the books under the `finance: company books` permission.
4. **Granting roles:** HR administrators can grant any role, including company administrator. Target: grantable roles (below).
5. **Deactivated users:** making someone inactive doesn't remove their access. The per-request member status check (Track 1) fixes this.

## Beyond module × action

The roles guide needs things a grid of module × five actions can't express. Build these into the data model from the start; adding them later means migrating every role assignment.

| Need | Example from the roles guide | How the matrix supports it | When |
| --- | --- | --- | --- |
| **Which records a grant covers ("scope")** | A client can use contractor bills, but sees only the bills on their own project; a project manager acts only on their own projects; a foreman sees only their crew's tasks; an employee sees only their own leave | Every grant carries a scope as well as actions (see [Scope](#scope-which-records-a-grant-covers)) | Data model now; scoped checks module by module |
| **Named permissions within an area** | Certify a bill; see the company books; sign off a safety defect | Named permissions on a row, such as `progress-bills: certify`, `finance: company books` and `inspections: sign off safety`. They show as extra checkboxes on that row. | Data model now |
| **Line-manager approvals** | A supervisor approves their crew's leave without any company role | The reporting-line rule stays next to the matrix | Already exists |
| **Preparer never approves** | Whoever certifies a bill doesn't approve it; an accountant doesn't approve their own entry | A shared check on every approve-type permission: the approver must differ from the record's preparer. An owner override is recorded. | Data model now (the preparer is stored on records); checks module by module |
| **Approval limits** | Each approving role has a spending limit; above it, approval goes up a level | An optional amount on a role's approve permission, compared with the record's amount | Later, starting with bills and purchase orders |
| **Grantable roles** | HR gives ordinary roles; only the owner or IT gives senior and admin roles | Each role lists which roles its holders may grant. The Roles & Permissions tab enforces it. | Data model now |
| **Warning on risky combinations** | Two roles that together let one person prepare and approve the same thing | A warning in the Roles & Permissions tab when a user's roles combine a preparing and an approving permission on the same row | Later |
| **Outside parties** | Client, consultant, subcontractor, vendor | External roles whose grants use the Related scope, and a link from the person to their customer or vendor record | After scopes are in place |
| **Access ends with employment** | Deactivating someone removes their access at once | Per-request member status check | Track 1 |

### Scope: which records a grant covers

"Related" (called "Limited" in early drafts) restricts which records a person can reach, not which fields they see. A client given contractor bills can open them, but only the bills connected to their own project, and they see those bills in full. So every grant has a scope on top of its actions:

| Scope | Covers | Typical holders |
| --- | --- | --- |
| **All** | Every record in the company | Company leadership, department heads |
| **Assigned projects** | Records on projects the person is a member of | Project managers, site staff, supervisors |
| **Related** | Records linked to the person: their own project as a client, their own bills and work packages as a subcontractor, the items assigned to them | Clients, consultants, subcontractors, vendors, workers |
| **Own** | Records about or created by the person themselves | Everyone, for their own leave, attendance and profile |

How it works:

- **One cell holds actions and a scope.** In the matrix a cell reads, for example, "View · Related". The same role can have All on one row and Related on another.
- **Assigned projects uses project membership.** Projects already have members, so this scope reuses that membership instead of a new list.
- **Related needs a link between the person and the record.**
  - **Outside parties:** a link from the user to their customer or vendor record, so records carrying that customer or vendor are theirs.
  - **Staff:** the assignee on tasks and inspection items.

  Each module says which field ties its records to a person: for a bill the subcontractor and project, for a task the assignee.
- **Own is the existing self rules,** written as a scope so the matrix can show it.
- **Checks filter as well as allow.** For a list, the check decides whether the person may open the area at all, and the scope filters which rows come back. For a single record, both apply. Lists must be filtered in the query, not after loading, so counts and paging stay right.
- **Related and Own stay separate scopes.** Both mean "records connected to me", but they're granted separately for more control. A worker can have Own on leave (their own requests) without Related (their crew's). A client can have Related on bills without anything they merely created counting as theirs.
- **Combining grants.** When a user holds the same row through several roles or groups, the scopes add together. All covers everything, and Assigned projects covers every record on those projects. Related and Own each add their own records.
- **A baseline that can't be removed.** The Member role grants Own on leave, attendance and profile, and that grant can't be removed. Nobody loses access to their own records by mistake.

Hiding individual fields, such as a supplier's bank details from a store keeper, is a separate and smaller rule that the system already has. It stays as it is and isn't what Related means.

The roles guide's proposed structure has 27 roles, from owner to labourer plus outside parties. None of it is needed on day one, but this model can express all of it. Once it's live, the 27 roles become optional templates an org can add.

## What to do next, in order

1. **Review this mapping**, in particular:
   - the seven new matrix rows and the 12-area grouping
   - the 51 approve endpoints
   - the bill steps
   - the seeding questions above
2. **Check one staging token and one prod token** for a Keycloak permission such as `vendor:read`. If nobody holds them, mark the `hasAuthority` endpoints in the CSV as retire or convert.
3. **Build the matrix tables** with the parts from [Beyond module × action](#beyond-module--action) that are marked "now": a scope on every grant (All, Assigned projects, Related, Own), named permissions within an area, grantable roles, and the stored preparer. Then build the permission lookup and the `<module>:<action>` authorities in `JwtAuthConverter`.
4. **Seed the standard roles in every org from this table**, and turn each user's current Keycloak group memberships into role assignments.
5. **Convert the checks module by module.** Each conversion runs the module's `*AuthzTest` and uses the CSV as the checklist. Start with the smallest: `chat`, `assets`, `construction`.
6. **After go-live, fix the [weak spots](#weak-spots-copied-on-day-one)**, starting with attachments and contractor bills.
